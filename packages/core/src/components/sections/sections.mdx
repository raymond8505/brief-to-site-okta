# Section suite

A **section** is one full-width horizontal band of a page — a hero, a feature grid, a closing
call to action. Sections are the largest composable unit: a page is a stack of them. Each is a
compound family whose slots are filled with **blocks**, the smaller presentational leaves.

Browse the suite in the **Sections/\*** tree, and the block vocabulary in **Blocks/\***. Each entry
documents its own slots, variant axes and tokens. This page is the contract they all follow.

## The contract

1. **Render through `Section`.** The shell is a full-bleed `<section>` that provides the standard
   centred container (`max-w-7xl`, default breakpoints, responsive gutters) and the one variant axis
   shared by all sections: spacing **density** (`compact` / `comfortable` / `spacious`). Because it is
   full-bleed, a section may carry its own background on the outer element while its content still
   lands on the shared column.
2. **A section is a compound family, filled with blocks.** Like the `Card` family, a section is a
   root plus **named slot subcomponents** (e.g. `Hero` + `HeroBody` / `HeroMedia` / `HeroAside`), each
   carrying a `data-slot`. Fill those slots with **block primitives** from
   `@brief-to-site/core/blocks` — never ad-hoc markup. **A "variant" is a composition**: the same
   section reads as _split_, _centered_, _with-stats_, or _quote-led_ purely by which blocks fill
   which slots. A section still owns any genuine geometric layout as a small **CSS-only CVA**
   (`align`, `mediaSide`, `columns`, `formSide`); and layout may react to which slots are present via
   `has-[data-slot=…]`. A quantity axis takes **numbers**, never number-words — `columns={3}`, not
   `columns="three"`. A dev-only `assertAllowedChildren` guard warns when a wrong component is
   composed into a slot.
3. **Images go through the `MediaFrame` block.** No section renders a raw `<img>`. `MediaFrame` takes
   a `src` path (the root-relative `/images/<name>.png` a placeholder manifest entry generated) in an
   `object-cover` box — so an operator overwrites art of any size without resizing. When `src` is
   omitted it falls back to an inline placeholder sized from its `aspect`.

Colour: sections and blocks consume **role tokens** (`bg-background`, `text-foreground`,
`text-muted-foreground`, `bg-muted`, `--brand-secondary`) — never hardcoded colours — so the
deterministic theme stays orthogonal. Each component's story documents the tokens it consumes.

## Group blocks take data, not children

Sections are compound (a root plus named slot subcomponents, above). **Blocks are not, by default.**
The rule:

> A block that renders a **homogeneous repeated set** takes a data array and builds its own rows. A
> block that wraps **arbitrary or heterogeneous** content keeps `children`.

`BulletList` (`items`), `StatRow` (`stats`) and `LogoRow` (`logos`) take data. `CtaGroup` (arbitrary
`Button`s with their own hrefs and variants), `PriceCard` (a heterogeneous slot — a `BulletList` _and_
a CTA) and `Prose` / `Quote` / `FaqItem` (free-form rich text) keep `children`.

This isn't stylistic. A parent cannot pass a prop to children it did not construct — the mechanism
for that is context, and core's blocks are **Server Components**, where React's `react-server` build
exports no `createContext`. Composing a repeated set as children therefore forces
`React.Children.map` + `cloneElement` + fragment-unwrapping to reach the items, and the item shape can
only be checked by a dev-only `assertAllowedChildren` warning. A data array replaces all of it with an
ordinary prop and a **compile-time** type.

The convention, so the next group block is mechanical:

- Export a named item interface — `<Component><Singular>` (`LogoRowLogo`, `BulletListItem`,
  `StatRowStat`) — declared **above** the props interface, with per-field JSDoc.
- The array prop is **required** and named for its plural noun (`items`, `stats`, `logos`) — the shape
  is uniform, the noun stays semantic so it reads at a call site.
- Props still extend the DOM element props; the array is additive. Key by index (these lists are
  static and never reorder).
- No item subcomponent. A `<li>` or a `<dt>`/`<dd>` is invalid outside its parent anyway, so exporting
  one only invites misuse.
- No `assertAllowedChildren` — the type is the contract.

## The bound is the block vocabulary

Content order carries no constraint — a11y is out of scope here (the deliverable is full-page
screenshots), so a section arranges its slots and blocks however reads best. What keeps output
deterministic is the **bounded set of block primitives** composed from, the typed slot props, and the
dev-only slot guard: a bounded vocabulary in place of free-form markup. Compose from the published
blocks first; when the vocabulary falls short, **extend it deliberately** — a new block, built the
same way you would a `ui/` primitive. Never drop raw JSX into a page.

## What earns a place in core

A core section is **purpose-built**: it exists to present one _specific kind of content_, and its slots
have a closed block vocabulary that says so — `ArticleGrid` holds `ArticleCard`s, `Steps` holds
numbered `Step`s, `PricingTiers` holds `PriceCard`s, `Hero` opens a page. Name the content and the
section's reason to exist follows.

A **generic arrangement** is not a section — "N columns under a title", "copy beside media" — it is a
_composition pattern_. Core deliberately carries no stand-in for them: a generic section is a magnet
that pages get force-fit into, and re-composing the pattern where it's needed is cheap and is the
intended cost. So "no core section fits this" is an ordinary outcome, not a shortfall.

## Building a new section

Copy **`components/sections/_template/`** (see **Sections/\_Template**), rename the files + symbols,
and replace the body. It is a minimal, green, story-documented compound section — the trustworthy
starting point for all three rules. Export the new section from `components/sections/index.ts` (the
`_template` itself is intentionally not exported).
